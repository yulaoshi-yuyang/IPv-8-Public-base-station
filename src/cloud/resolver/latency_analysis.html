1 当前 CachedStore 读路径瓶颈解剖

逐行分析 get() 热路径，量化每次操作的纳秒级开销。

# 代码位置 操作 估算延迟 严重度 分析
1 borrow_mut() RefCell 借用检查 ~2ns 低 运行时检查 is_borrowed 标志位。单线程无竞争，但每次 get() 必付。
2 contains_key(addr) HashMap 查找 #1 ~80-120ns 严重 std HashMap 默认用 SipHash-1-3（DoS 防护），每次哈希计算 ~80ns。IPv8Address 是 128-bit 值，哈希开销在此量级。
3 cache.get(addr).unwrap() HashMap 查找 #2 ~80-120ns 严重 命中后再次查找取值——重复计算哈希。应改用 entry() 或 get_key_value 合并。
4 entry.clone() 深拷贝 Entry ~150-300ns 严重 Entry 含 NodeRecord，其中 tunnel_entry: String（堆分配 + memcpy）、alt_entries: Vec<String>、local_candidates: Vec<String>——每次命中都深拷贝。
5 get_mut(addr) HashMap 查找 #3 ~80-120ns 严重 第三次哈希查找，仅为更新 last_access。三次查找 = 3x 哈希计算 = ~240-360ns 浪费。
6 Instant::now() 系统时钟读取 ~15-30ns 中 仅在负缓存路径触发。Windows 上 QueryPerformanceCounter 系统调用。正命中路径不触发，但负缓存路径每次必付。
7 clock.wrapping_add(1) 逻辑时钟更新 ~1ns 低 整数加法，可忽略。但配合 #5 的查找，整体路径变长。
8 evict_if_needed (写入路径) O(n) 全表扫描 ~5-50µs 中 仅在超容量时触发（写入路径），读路径零开销。但 10K 条目时单次淘汰扫描 ~50µs，批量写入会形成延迟尖峰。
9 stats.clone() 统计快照拷贝 ~5ns 低 4 个 u64 = 32 bytes memcpy。非热路径（仅在查询 stats 时），不影响 get()。

2 业界超低延迟方案对标

hashbrown + aHash Rust

SwissTable 设计，SIMD 加速指纹匹配，AES-NI 哈希

哈希计算 ~5-10ns
vs SipHash-1-3 8-15x 更快
CPI (3GHz) 1.0
生产就绪 高

std HashMap 内部已用 hashbrown，但默认哈希器仍是 SipHash。切换 aHash 可在保持 SwissTable 查找的同时加速哈希计算。

SLRU 缓存 算法

分段 LRU，热冷分区，抗扫描污染

GET 延迟 40-260ns
吞吐 8-12M ops/s
命中率 优秀
vs 纯 LRU 命中率 +10-20%

热区保护高频 key 不被扫描驱逐。当前实现用逻辑时钟 O(n) 扫描淘汰，SLRU 可在 O(1) 淘汰的同时提升命中率。

Arena 分配器 内存

bumpalo / arena-b，连续内存批量回收

单次分配 ~4.7ns
vs Box::new ~9x 更快
碎片 无
适用场景 Entry clone

当前每次命中深拷贝 Entry 含 String 堆分配 ~200ns。用 arena 可将分配降至 ~5ns，但需解决生命周期管理。

mimalloc 系统级

微软官方全局分配器替代

多线程分配 5.3x 提升
RSS 减少 ~50%
Windows 兼容 是
接入方式 #[global_allocator]

一行代码全局替换，所有堆分配受益。尤其减少 String/Vec 分配尾延迟。

DashMap 分片 并发

分片锁，无全局争用

读延迟 <1µs
vs Mutex HashMap 2-4x 更快
当前瓶颈 RefCell 不可并发
128B 对齐 防 false sharing

当前 RefCell 不可跨线程。若后续多线程 gRPC，需切 DashMap。128 字节对齐防止 Intel 相邻行预取导致的伪共享。

SmallVec 栈上分配 内存

短 Vec/String 不上堆

空 Vec 分配 ~40ns → 0ns
alt_entries (空) 栈上
local_candidates (空) 栈上
clone 开销 大幅减少

NodeRecord 的 alt_entries 和 local_candidates 在大多数节点为空 Vec，但每次 clone 仍触发堆分配。SmallVec/ArrayVec 可将空/小 Vec 完全放栈上。

3 当前实现 vs 优化后对比

🔴 当前实现

fn get(&self, addr: &IPv8Address) -> Option<Entry> {
    let mut state = self.state.borrow_mut();

    // 第1次哈希: SipHash ~100ns
    if state.cache.contains_key(addr) {
        state.stats.hits += 1;
        state.clock = state.clock.wrapping_add(1);
        let clock = state.clock;

        // 第2次哈希: SipHash ~100ns
        let entry = state.cache.get(addr)
            .unwrap().entry.clone();
        //        ^^^^^ 深拷贝 ~200ns
        //        (String + Vec<String> x2)

        // 第3次哈希: SipHash ~100ns
        if let Some(existing) = state.cache.get_mut(addr) {
            existing.last_access = clock;
        }
        return Some(entry);
    }
    // 总计: ~504ns (命中路径)
}

🟢 优化后实现

fn get(&self, addr: &IPv8Address) -> Option<Entry> {
    let mut state = self.state.borrow_mut();

    // 单次哈希: aHash ~8ns + entry() 原子操作
    if let Some(ce) = state.cache.get_mut(addr) {
        state.stats.hits += 1;
        state.clock = state.clock.wrapping_add(1);
        ce.last_access = state.clock;

        // Arc 共享指针 clone ~5ns
        // 或 SmallVec 栈上拷贝 ~20ns
        return Some(ce.entry.clone());
    }
    // 总计: ~33-53ns (命中路径)
    // 提升: ~10-15x
}

4 优化路线图（按优先级）

P0 — 立即收益
  • 合并三次哈希：用 get_mut() 一次完成查找+更新
  • 切换 aHash：替换 SipHash，~12x 哈希加速
  • Arc<Entry>：clone 从 ~200ns → ~5ns
P1 — 中等收益
  • SmallVec：空 Vec 栈上化，减少堆分配
  • mimalloc：全局分配器替换
  • LRU O(1) 淘汰：双向链表 + HashMap
  • likely/unlikely：分支预测提示
P2 — 长期演进
  • DashMap 分片：多线程并发读
  • SLRU 热冷分区：命中率提升
  • prefetch 指令：CPU 预取
  • NUMA/CPU 绑核：系统级

实施时间线

P0: 合并哈希 + 切换 aHash 预计 2h

将 contains_key + get + get_mut 三次查找合并为单次 get_mut。替换 std::collections::HashMap 为 hashbrown::HashMap<K, V, ahash::ABuilder> 或直接用 ahash::AHashMap。

预计延迟降低 504ns → ~120ns
改动范围 cached_store.rs + Cargo.toml

P0: Arc<Entry> 共享指针 预计 1h

将 CacheEntry.entry: Entry 改为 CacheEntry.entry: Arc<Entry>。命中时 Arc::clone() 仅原子引用计数 +1（~5ns），不做深拷贝。Store trait 的 get 返回类型改为 Arc<Entry>。

预计延迟降低 120ns → ~30ns
改动范围 lib.rs (Store trait) + cached_store.rs + 调用方

P1: SmallVec + mimalloc 预计 3h

NodeRecord 的 alt_entries 和 local_candidates 改为 SmallVec<[String; 4]>。同时引入 mimalloc 全局分配器。空 Vec 从 ~40ns 堆分配 → 0ns 栈上。所有 String 分配经 mimalloc 加速。

预计延迟降低 30ns → ~25ns

P1: LRU O(1) 淘汰 预计 4h

当前 min_by_key 全表扫描 O(n)。改用双向链表 + HashMap 的经典 LRU：HashMap 存 key → 链表节点指针，淘汰时弹出链表尾部 O(1)。10K 条目时从 ~50µs → ~10ns。

淘汰延迟（10K 条目） ~50µs → ~10ns

P2: DashMap + SLRU 预计 8h

引入 DashMap 替代 RefCell+HashMap，实现多线程并发读。升级 LRU 为 SLRU（热冷分区），提升命中率 10-20%。128 字节对齐防止 false sharing。

并发读延迟 <1µs (多线程)

5 P0 具体代码方案

优化1: 合并三次哈希 → 单次 get_mut

当前：3 次哈希

// 第1次哈希
if state.cache.contains_key(addr) {
    state.stats.hits += 1;
    // 第2次哈希
    let entry = state.cache
        .get(addr).unwrap()
        .entry.clone();
    // 第3次哈希
    if let Some(existing) =
        state.cache.get_mut(addr) {
        existing.last_access = clock;
    }
    return Some(entry);
}

优化后：1 次哈希

// 单次哈希，同时拿引用
if let Some(ce) = state.cache.get_mut(addr) {
    state.stats.hits += 1;
    state.clock = state.clock
        .wrapping_add(1);
    ce.last_access = state.clock;
    return Some(ce.entry.clone());
}

优化3: Arc<Entry> 替代深拷贝

use std::sync::Arc;

struct CacheEntry {
    entry: Arc<Entry>,  // 共享指针，clone 仅 +1 引用计数
    last_access: u64,
}

// Store trait 改动
pub trait Store {
    fn get(&self, addr: &IPv8Address) -> Option<Arc<Entry>>;
    //                                  ^^^^^^^^^^^^
    //                                  Arc clone: ~5ns
    //                                  vs Entry clone: ~200ns
}

// 写通路径
fn insert(&mut self, addr: IPv8Address, e: Entry) {
    let arc = Arc::new(e);  // 一次分配
    self.inner.insert(addr, Arc::clone(&arc));
    state.cache.insert(addr, CacheEntry {
        entry: arc,
        last_access: clock,
    });
}
