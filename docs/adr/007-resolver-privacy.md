# ADR-007: Resolver 隐私模型

状态: Accepted（2026-09-05，Phase 3 M1 决议）
关联: ADR-021（自托管云）, protocol-spec §10.4, v9 §Phase 3

## 背景

Resolver 是"域名 → 隧道入口 + 能力标记"的中心查询点（v9 定 gRPC 原子返回）。
客户端每次通信前都要问它"我要找的 agent 在哪"——运营方因此天然获得
**通信关系图**（谁在什么时候找谁），这是叠加网络最大的隐私泄露面。
v9 Phase 3 要求评估三个候选：ODoH、多层 Resolver 架构、本地缓存 + TTL。

## 威胁模型

- **对手**：Resolver 运营方（半诚实：诚实执行协议但记录并分析查询）。
- **想保护**：查询者身份（client_ipv8_addr）与被查询名（query_name）的
  关联关系；查询时间模式。
- **不在本轮范围**：流量分析（观察 UDP 元数据的网络对手）、被查询方
  主动暴露入口 IP（入口本身是公开可达信息）。

## 候选与评估

1. **ODoH（Oblivious DNS-over-HTTPS）**：查询经代理+权威两跳，双方各见一半。
   隐私最强，但需要独立代理运营方与 HTTPS 栈，部署复杂度与自托管目标
   （ADR-021）冲突，且 v9 的 Resolver 是 gRPC 而非 DNS——协议不对口。
2. **多层 Resolver（根/权威分离）**：根只做指向、权威只收转发查询。
   单层部署（自托管常态）下两层同机，无实际收益。
3. **本地缓存 + TTL + 最小披露**：Resolver 只返回路由必需字段，
   客户端长缓存、聚合查询；运营方仍可见"谁查了什么"，但频率大幅降低。

## 决策

**Phase 3 落地方案 3（最小披露 + 缓存 TTL），并保留升级接口。**

- resolver.proto（v9 §695 权威定义）字段即最小集：入口 IP、ipv8_capable、
  mtu、alt_ips、ttl——**不返回**被查询方精确位置历史、不要求查询方出示
  身份凭据（匿名查询）；
- 客户端 MUST 尊重 ttl 并实现本地缓存（减少查询即减少泄露面）；
- Resolver 端 SHOULD NOT 持久化查询日志；审计日志（若有）MUST 匿名化
  client_ipv8_addr 的 HostID 低位。
- 方案 1/2 记为后续演进路径：跨信任域部署普及后重新评估 ODoH 变体
  （gRPC + HPKE 封装），本 ADR 届时可被取代（Superseded）。

## 后果

- ipv8-resolver（M4）实现即按最小披露字段集设计，无额外密码学栈；
- 隐私声明写入 README：自托管部署下 Resolver 运营方可见查询关系图，
  对隐私敏感的用户应自建（与 ADR-021 叙事一致）。
