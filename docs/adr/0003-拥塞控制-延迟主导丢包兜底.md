# ADR 0003 — 拥塞控制：延迟主导 + 丢包兜底（--cc，默认关闭）

## 背景

裸 UDP 数据面没有拥塞控制：跨公网场景打爆对端队列（bufferbloat）或自饿
（自己发的回执/信令挤不进自己塞满的队列），RTT 预算（<200ms）失守。
停车场 2026-09-19 入行，前置件观测底座（ADR-0002）已落地——丢包率与 RTT
信号现成，CC 在 `ingest_report` 同一函数顺手推进，零新管道。

v1 定位是**保护性限速**：防打爆队列/自饿，不抢满带宽。2026-10-14 用户裁决
两项钉死：①算法=延迟主导+丢包兜底；②限速口径=线上总字节（main+alt+FEC
恢复帧全计入）。

## 决定了什么

1. **算法（CongestionController，ipv8-observe/src/cc.rs）**：每份对端回执推进一次。
   - 起步 = ceil/4（慢启动，避免开局即打爆）。
   - 降（乘性）：RTT ≥ min_rtt×1.25（膨胀判据，延迟主导）**或** union 丢包率
     ≥30‰（丢包兜底）→ rate ×7/10，不低于 floor=max(ceil/16, 64kbps)。
   - 增（加性）：好窗 → rate + ceil/8，不超 ceil。
   - 冻结/累积口径：单份对端报告窗固定 200ms，低 ceil 下每窗期望样本
     ≪32；按**累积**推进——多份报告累加到 min_expected=32 再评估一次
     （累积期内速率与 min_rtt 基线全冻结），高帧率下首份即达标、等价逐份
     评估（无回归）。RTT 信号缺失（回执未往返）只判丢包。
     2026-10-14 真机首轮暴露旧逐份口径缺陷（D1）：低 ceil 数学上恒冻结在
     起步值，改累积后 [stats] cc_rate 可推进并达 ceil。
   - min_rtt 基线：更低样本即时刷新；超 10s 未刷新则重置为当前 RTT
     （链路切换后防旧基线锚死，把新常态误判为永久膨胀）。
2. **限速执行（wintun-node Pacer）**：批粒度令牌桶。出站批循环在既有
   observe 临界区顺手读 `cc_rate_bps()`；统计本批实际放上 socket 的线上总
   字节（main + alt + 恢复帧全计），批后按速率 sleep 追平；桶容量 = 50ms
   等值字节（吸收 TUN 批突发，又不积压失控）。锁序守既有规矩
   （observe→engine→sched），pacer 锁不嵌套。取证口：`[stats]` 行附带
   `cc_rate=`（当前 bps，--cc 关为 off）——真机验收直读，不靠吞吐反推
   （反推会被爬坡窗口污染）。
3. **形态**：`--cc` 开关默认关闭（与 --mp/--fec 出货形态一致，关时
   pacer=None 直通零开销）；`--cc-ceil <kbps>` 在 --cc 时必填且 >0，
   未开 --cc 单给 --cc-ceil 报错。
4. **已知边界一**：分片活跃路径（--shards>1 且 Established 后）经 hub 提前
   return，不经 Pacer——与 mp/fec 在分片期暂停是同一既有形态：性能档下
   保护性限速让位。要组合"分片+限速"需重审本 ADR。
5. **已知边界二（D2，2026-10-14 真机验收暴露，登记 debt.md）**：Pacer 的
   `wait` 内含 `sleep` 且该 sleep 落在 **TUN 读线程内**（`spawn_tun_reader`
   → `dispatch_tun_batch` 单线程）——批后追平睡眠期间 wintun 环无人排空，
   灌包期环溢出丢包：①同一环 FIFO 上的延迟敏感流（ICMP）被灌流挤到
   满载 0/5（CC 关闭对照 5/5）；②溢出丢包被对端观测到 → CC 丢包兜底触发
   → 速率锯齿回落（爬满 ceil 后连降 5 窗到 floor 再爬）。根因是"限速与
   环排空同线程"，正解=把限速从读线程剥离（独立发送线程/有界队列）或
   引入优先级（接线 ipv8-qos，见停车场 QoS 行）。修前不得默认开启 --cc。

## 为什么（考虑过的替代方案）

- **纯丢包派（Reno 式）**：队列塞满才见丢包，RTT 早已爆掉——违反
  <200ms 预算，否。
- **纯延迟派（BBR 式）**：RTT 信号失真时（对端 CPU 抖动、回执路径不对称）
  无最终防线；且与 FEC 门控读同一份丢包信号时，丢包兜底被阉割后两策略
  对同一链路状态判断不一致。否；保留丢包作兜底。
- **逐包令牌桶**：逐包取锁/取时钟开销大；批粒度（≤64 包一批）统计与追平
  足够平滑，且与既有"批级读一次出站策略"模式同构。
- **只计 main 字节**：alt 双发与 FEC 恢复帧是真实线上负载，漏计即限速
  口径失真（裁决钉死：线上总字节）。
- **速率变化打 info 日志**：CC 速率随每份回执变动（5Hz），打日志必刷屏；
  与熔断/门控的"翻转才打"不同，故不打。

## 什么条件下可以推翻

- 真机验收（netbench UDP 2×ceil 打流）出现：RTT 仍超预算、吞吐收敛不到
  ceil 附近、或信令被限速挤断——先调参数（膨胀阈值/降增步长/桶容量），
  调参无效再重审算法形态。
- 需要"分片性能档 + 限速"组合时，Pacer 须下沉到分片 worker 出口，重审
  第 4 条边界。
- 观测底座信号面整体改版（ADR-0002 被推翻）时，本 ADR 一并重评。
